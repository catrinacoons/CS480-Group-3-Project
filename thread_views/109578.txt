## Summary

Adds the HID Service (HIDS), the GATT service the HID Device role of HOGP is built on, a `hids` Bluetooth shell command set, and a two device bsim test.

Follows the Bluetooth WG decision in https://github.com/zephyrproject-rtos/zephyr/pull/109578#issuecomment-5526424590: HIDS lands as a standalone service under `services/hids/`, the HOGP Device wrapper that only forwarded to it is dropped, and `profiles/` is left to the HOGP Host role, which is a real profile rather than a stub. So there is no `profiles/` directory and no `bt_hogp_device_*` API here.

Phase 1 of RFC #108582.

## Design notes

* **The attribute table is static.** How many Report characteristics of each type exist is Kconfig; the application supplies one Report ID per characteristic at registration. Building it at runtime would mean either exposing Reports the application does not use, or putting a CCC on Output and Feature Reports, which HIDS does not define.
* **The service holds each Report value** and answers a Host read from it, like the other GATT services in the tree. Every fragment of a long read comes from that one value rather than from a per-read copy that can go stale. The application uses `bt_hids_report_set()` and `bt_hids_report_get()`; a Host write to a writable Report replaces the value too.
* This replaces an earlier `get_report` callback per read. ATT does not read a long attribute atomically, so a per-read callback cannot stay consistent without a cache whose lifetime ATT gives no way to bound. Two consequences: memory becomes one buffer per Report instead of per connection (336 to 1096 bytes of static data with 1/1/2 Reports at `MAX_REPORT_LEN=256`), and the application is no longer told that a Host did GET_REPORT.
* **Protocol Mode and Suspend are per connection**, held in a slot from a pool of `MIN(CONFIG_BT_MAX_CONN, CONFIG_BT_MAX_PAIRED)` slots, claimed when a Host's link is encrypted or on its first Protocol Mode or HID Control Point access, and reset on every connection. A Host that finds the pool full when it encrypts is simply not tracked. CCC changes are reported with the connection they belong to.
* **Writes are bounded.** Longer than `CONFIG_BT_HIDS_MAX_REPORT_LEN` gets Invalid Attribute Length, so that option bounds both directions; a non-zero offset gets Invalid Offset, because a Report is a whole report rather than a byte addressable blob.
* **Checked at registration:** Report Map length, duplicate Report IDs within a Report Type, a Report ID of 0 when a type has several Reports, and HID Information flags the service cannot back.
* **Protocol Mode is off by default** and selected by the two Boot Report options, because the characteristic is mandatory only for a Device that supports Boot Protocol Mode.
* **Boot Reports** take their layout from the USB HID Specification rather than the Report Map, so they have no Report Reference descriptor, and only the two Boot Input Reports have a CCC. Keyboard and mouse get separate options because HIDS v1.1 Table 2.1 allows each only on that device type. Staying inside the selected Protocol Mode is the Host's requirement, so neither set is restricted; the application picks what to send from `bt_hids_get_protocol_mode()`.
* **Not implemented:** multiple HID Service instances, the External Report Reference descriptor, HID ISO.

## Test plan

* **bsim, two devices** (`tests/bsim/bluetooth/services/hids`): the client encrypts the link, discovers the service, checks the Report Map, the HID Information and every Report Reference descriptor, subscribes, then exercises GET_REPORT, SET_REPORT, Protocol Mode and the HID Control Point. It reconnects and checks that Protocol Mode is back at its default and notifications resume, that unregistering does not disconnect the Host, and that registering again while that Host is connected tracks it.
* Also in bsim: the three Boot Report characteristics (properties, which of them have a CCC, each fixed length, a Boot Keyboard Input notification, and a wrong length write refused before the application sees it); the registration checks; the bound `bt_hids_send_report()` enforces; a CCC write asking for indications refused while a Reserved bit is processed as zero; a Read Long, and a Read Blob at and past the end of the value.

*--- Copilot (2026-05-22 06:43:43+00:00)
`bt_hogp_device_register()` uses the `callbacks` pointer as the “registered” flag (`if (callbacks) ...`), but then assigns `callbacks = param->cb` without requiring it to be non-NULL. If `param->cb` is NULL, the service can be registered successfully while later APIs (e.g. `bt_hogp_device_send_report()`) will return -ESRCH and connection callbacks won’t run (`hogp_dev_connected` bails out on `!callbacks`). Use a separate registration state variable (or require `param->cb != NULL`) so registration and callback presence are not conflated.

*--- Copilot (2026-05-22 06:43:44+00:00)
`bt_hogp_device_unregister()` may double-unref `bt_conn` objects: it calls `bt_conn_disconnect()` (async) for each stored connection, then immediately iterates `connections[]` and `bt_conn_unref()`s any non-NULL entries. If the disconnect callback (`hogp_dev_disconnected`) runs after the manual unref loop, it will unref the same connection again. To avoid a potential refcount underflow/use-after-free, either unref+NULL the slots synchronously in `unregister()` (and make the disconnect cb ignore missing slots), or defer unref until the disconnect callback completes.

*--- Copilot (2026-05-22 06:43:44+00:00)

*--- chengkai15 (2026-05-25 13:37:49+00:00)
that a good question .here are  two possible approaches:

  Option A: Pure HIDS Service (bt_hids_*)
  - Register GATT attribute table, forward all events to app
  - App owns all state (protocol mode, suspend, report caching)
  - App must handle GATT read/write semantics directly
  - Simpler implementation, but more burden on app developers

  Option B: HOGP Profile (bt_hogp_device_*) — current approach
  - Profile manages internal state, app receives high-level notifications
  - App focuses on HID business logic, not GATT details
  - Follows the pattern of VCP (manages volume state), nRF bt_hids
    (manages protocol mode per-connection), and BTstack hids_device
    (stores protocol_mode + suspend internally, emits events)

 What the profile layer currently provides beyond a raw service:

  | Aspect | Pure Service | This Profile |
  |--------|-------------|-------------|
  | Protocol Mode | App stores + returns on read | Profile stores, serves reads, notifies app of changes |
  | Suspend | App stores + decides behavior | Profile tracks state, app queries via is_suspended() |
  | GET_REPORT | App manages GATT read buffer | Profile handles GATT, calls app synchronously (CTS pattern) |
  | Security | App configures permissions | Profile enforces via depends on BT_SMP + encrypted attrs |
  | Connections | App tracks refs | Profile manages lifecycle, prevents double-unref races |
  | Host discovery | App does manual GATT discovery | bt_hogp_host_connect() orchestrates HIDS+DIS+BAS (#109579) |

  I believe Option B (profile) is more useful for application developers — it's the approach taken by nRF Connect SDK, BTstack, and ESP-IDF for their HID Device implementations. None of them expose raw GATT
  events; they all internalize protocol mode and suspend state.

  That said, if you'd prefer Option A (land as pure bt_hids_*`service first, add profile wrapper later), I'm open to that path too.

@jhedberg @Thalley — let me boil this down to a concrete choice for the WG meeting.

The "samples vs subsys API" question decides this PR, so let me be honest about it: the HOGP Device layer is a thin wrapper — register/send_report/get_protocol_mode are basically one-line calls into the HIDS service, and the only real logic is requesting security on connect. HIDS (the service) is a third, cleaner case. That's the "standalone service, profile on top" pattern Thalley said he'd like to see more of, and the Host role would reuse those shared definitions directly.

- (A): everything becomes a sample like peripheral_gap_svc — no public API. Simplest, but the 18-state Host machine as unshared sample code is a lot to ask an app to copy, and there's no reusable service.
- (C): keep both roles as profiles under profiles/ and let the Device wrapper earn its keep later (GET_REPORT caching, validation). Bigger effort on the Device side; the Host side already meets this bar today.

I'm fine with (B) or (C) and can rebase #109579 onto whichever layout you land on. I'll hold off on more restructuring until then.

*--- Copilot (2026-09-19 09:05:14+00:00)

*--- Copilot (2026-09-19 09:05:14+00:00)
Every ATT Read and Read Blob request reads the mutable `ctx->value` and `ctx->value_len` again.
