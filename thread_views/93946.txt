*--- alwa-nordic (2025-08-01 12:12:46+00:00)
BTW, as I point out in https://github.com/zephyrproject-rtos/zephyr/discussions/93921, `bt_set_name` is unfortunately not thread-safe. We should think about how to make it or its replacement thread-safe when we define this observer APIs guarantees with regards to `bt_set_name`.

Shall there be one invocation of `name_changed` for every call to `bt_set_name`? In that case, we have to make `bt_set_name` into a blocking function, as it must block on a lock while the previous name is broadcast.

Maybe we should instead summarize `bt_set_name` so that multiple calls to it can coalesce to just broadcast the latest value? Should we then ensure the broadcast has distributed the value to all listeners so that all listeners see the name sequence? Or should we drop those and restart broadcast with the newest value as soon as possible?

Which thread should invoke the callbacks? Should it be done on the stack of `bt_set_name`? Then we have to be mindful of recursive calls to `bt_set_name`. It also makes `bt_set_name` be a deadlock hazard for the thread calling it. We also would not be sure how much stack space we have.

*--- Thalley (2025-08-04 09:14:18+00:00)
> I cannot agree. If application calls bt_set_name it has already a way to know that the name is going to be changed. The only unknown "point of change" is when it is changed via client using GATT write to GAP service.

There are cases where multiple applications are running on a device, each with their own advertising set (which is also why we want to have informational callbacks as a list of callbacks). If application A changes the name locally, then application B will still need to update the device name it is advertising. I agree with @alwa-nordic that local changes should still trigger callbacks. 

w.r.t. the thread issue, that's also something we are trying to deal with in the LE Audio implementation, where we have many cases of attribute values that may be changed locally or remotely. In those cases we are generally dealing with

1. Local application is reading or writing to modify a local value. This may occur in any thread, and any remote device may be writing or reading to the same value in the BT RX thread. For trivial values it's not a big issue, but for larger values that may need to be formatted on air, we use a mutex to lock the attribute, where remote access is guarded with a small timeout (e.g. 10ms in the read or write callbacks), and local access are guarded with K_NO_WAIT and will return an error immediately if the local change cannot occurs due to the mutex being locked
2. Notifications sent based on value changes are usually done in the system workqueue. The reason for this is that whenever a change is happening, we may not have free ATT buffers to send/enqueue the notification immediately. Handling the notifications in the system workqueue with a dirty-bit approach allows us to easily implement a retry-if-no-buffers solution. Any access to the resources here is also guarded, and if the mutex cannot be taken immediately we simply retry with a delay. 

We are not yet completely at a place where everything is properly guarded, or if the current solution is optimal, but it does work a lot better than doing nothing :)

*--- alwa-nordic (2025-08-04 12:05:49+00:00)
`bt_conn_cb_unregister()` does not have any thread-safety properties listed, and the implementation is also not thread-safe. And I think this is unfortunate and would like us to do something about this.

Your solution here is not any worse than what we already have as you point out. I did not mean that it's up to you alone to find an answer. But we need to think this through and discuss it. Since I think we want to revamp the whole name/appearance API we have a chance to do it properly.

I will insist that `bt_conn_cb_register()` and `bt_conn_cb_unregister()` should at the very least be thread-safe. It must be callable in a multi-threaded environment without corruption. The implementation uses `sys_slist` functions that are not all thread-safe.

Apart from that, I also think a developer would expect that last invocation of the callback to be unregistered is finished before `bt_conn_cb_unregister()` returns. This would be a nice guarantee to have, but it is a double edged sword. To fulfill this, `bt_conn_cb_unregister()` has to wait for any current invocation of the callback to finish. This is a hazard that we should document to warn the user if we have.

Alternatively, `bt_conn_cb_unregister()` can safely fail and return an error when the callback is currently in use. This may be the simplest option. We can have both blocking and non-blocking versions by e.g. taking a timeout parameter.

Finally, instead of a blocking in `bt_conn_cb_unregister()`, we can make the API asynchronous. This both frees up a user thread for other purposes, but importantly also draws attention to the fact that a unregister may be waiting for other stuff to finish.

I would like more discussion around this. Does anyone think differently than me about this?

Let's consider not implementing dynamic registration at all. Dynamic can always be implemented on top of static by the application or a convenience library.

There are multiple different approaches for such a library, so I expect there would be more than one such library. Like for your case, it would make sense to have static registration with initialization-time enabling. I think this can be more RAM-efficient than a generic dynamic registration, especially if we need locking and other bells and whistles.

We would want samples for various use cases to inform our users. One use case is for dynamic handlers during unit testing, where we would normally like to remove handlers specific to one test before running the next test. How to do this safely and conveniently is worth researching and documenting.
