TITLE: Add support for ICLegend S3KM1110 mmWave sensor

*--- opening post by kartben (2026-02-19 17:59:36+00:00)
This adds support for UART-based mmWave sensor from ICLegend S3KM1110.

The sensor is pretty configurable so a follow-up PR might introduce support for some custom attributes (e.g. to set the various "detection gates") but for an initial implementation the current version of the driver should be fine since the experience is already quite great out-of-the-box with default settings.

Also adds a new sample and a shield featuring the sensor.

*--- Copilot (2026-03-03 10:08:47+00:00)
`k_sem_take()` can fail for reasons other than a timeout (e.g. being interrupted). The current code maps any non-zero return to `-ETIMEDOUT`, which can mask the real error. Consider translating only the timeout case (typically `-EAGAIN`) to `-ETIMEDOUT`, and otherwise return the original error code.
```suggestion

		if (rc == -EAGAIN) {
			LOG_DBG("Did not receive a complete frame after %d ms",
				CONFIG_S3KM1110_UART_TIMEOUT_MS);
			rc = -ETIMEDOUT;
		} else {
			LOG_DBG("k_sem_take failed with error: %d", rc);
		}

		k_mutex_unlock(&data->lock);
		return rc;
```

*--- Copilot (2026-03-03 10:08:47+00:00)
The driver disables RX interrupts after receiving a single frame and only flushes the UART FIFO once during init. If the sensor streams frames continuously (no request/response is sent here), bytes can accumulate in the UART FIFO between `sensor_sample_fetch()` calls and overflow or leave the next fetch starting mid-stream. Consider either keeping RX enabled and continuously parsing frames in the ISR (storing the latest complete report), or flushing/discarding pending FIFO data right before enabling RX for a new fetch.

*--- Copilot (2026-03-03 10:08:47+00:00)
`S3KM1110_MAX_PAYLOAD_BYTES` controls the size of the UART receive buffer in the S3KM1110 driver, but this option has no lower bound, even though the driver assumes the buffer is large enough to hold at least the frame length header and base report payload. If a board configuration sets this value too small (e.g. 1), incoming UART frames can trigger out-of-bounds writes in the driver, corrupting adjacent kernel memory and allowing a malicious or compromised sensor module to crash the system or potentially gain code execution. Add a strict minimum (via a Kconfig `range` or equivalent compile-time check) so `S3KM1110_MAX_PAYLOAD_BYTES` cannot be configured below the minimum number of bytes required by the wire protocol.
```suggestion
	depends on S3KM1110
	range 8 65535
	help
	  Maximum payload size accepted from the radar report protocol.
	  Must be at least large enough to hold the frame header and the
	  smallest valid report payload.
```
