TITLE: serial: Add framing-error-reporting property

*--- opening post by DaAwesomeP (2026-06-20 23:45:03+00:00)
This PR adds property `framing-error-reporting` to UART drivers. This property allows a driver to expect how to actively handle a framing error if the next byte after a framing error needs to be read (for protocols like DMX512).

I am working on a DMX driver for Zephyr. DMX signals the start of a packet with a "Mark After Break" signal, which is interpreted as a framing error or break error on a UART. The next byte after the error is valid data that is a part of the packet. Normally, a line error would probably mean throwing away the data immediately before and after, but here I need to keep the data following the error. I have this working with Zephyr APIs on a bunch of platforms, but it is impossible for the driver to handle UART error handling type without knowing at compile time/runtime.

*--- DaAwesomeP (2026-07-24 17:36:53+00:00)
> No uart API integration needed?

It's a purely informational flag + enum for downstream drivers to use. How you actually want to handle the byte following the error really depends on the protocol. In some cases you want to keep the byte right after the error and in other cases you want to explicitly discard it (or multiple bytes). Example in this PR:
https://github.com/mitmedialab/zephyr/blob/49f3300c9c39af12fea3b035747d4c6433945e80/subsys/dmx/dmx_uart_isr.c#L79-L125

I'm also figuring out how to do this for async UART, but that will be more complicated and actually require API changes (mainly adding an event type). I have something working for that but will probably hold off on sending that until #112751 has some progress.

*--- DaAwesomeP (2026-07-28 19:04:20+00:00)
@sylvioalves thanks for pushing me on this. I am working on a `fifo_read_flagged()` which would be implemented in each driver. This removes the need to drain the buffer the way that the DMX RFC currently does. The downside is that if a driver is missing the implementation, a user can no longer simply define `framing-error-reporting` in DT to get it to work. But it does remove the drain solution I have now (which is less explicit).

To my knowledge the only common protocols that use breaks are DMX and LIN. If there are others that come to mind, please let me know and I will try to incorporate the requirements into my proposed solution (so that those could be contributed later).

Setting this to draft for the moment and will reopen once I confirm the other in-progress solution works/does not work.
