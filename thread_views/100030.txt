TITLE: twister: Support multiple ports in pytest-twister-harness

*--- opening post by gchwier (2025-11-25 13:37:33+00:00)
This PR adds support for multiple UART connections in `pytest-twister-harness`, enabling testing of multi-core applications where different cores communicate through separate UART interfaces.

Major Refactoring:
* Extracted connection logic from `DeviceAdapter` to new `DeviceConnection` class hierarchy
* Created specialized connection implementations:
  * `SerialConnection` for hardware UART ports
  * `ProcessConnection` for native simulation pipes
  * `FifoConnection` for QEMU FIFO communication

Each connection maintains separate log files (`handler.log` - for backward compatibility, `handler_1.log`, etc.) and can be accessed via `connection_index` parameter in device methods like `readlines_until()` and `write()`.
This enables testing multi-core applications where different cores communicate through separate UART interfaces.

Additional changes:
- Updated unit tests.
- Updated pytest-harness documentation, and docstring in API methods (like `readlines_until()`)
- Updated existing tests that used the `readline_until` method without an explicit `regex` parameter. Since `connection_index` has been added, the `regex` parameter must now be specified explicitly.

-  Updated `sysbuild/hello_world` sample - simplified dual UART testing
- Converted IPC ICMCG  sample from console harness to pytest harness. Added verification of both application and network core output

To run samples use:
```
$ZEPHYR_BASE/scripts/twister --no-clean -vv -ll debug \
--west-flash=--erase --device-testing --hardware-map ~/tmp/hardware_map.yml \
-T $ZEPHYR_BASE/samples/subsys/testsuite/pytest/shell \
-s sample.pytest.shell \
-s sample.harness.shell \
-T $ZEPHYR_BASE/samples/sysbuild/hello_world \
-s sample.sysbuild.hello_world.nrf54l15_cpuflpr \
-T $ZEPHYR_BASE/samples/subsys/ipc/ipc_service/icmsg \
-s sample.ipc.icmsg.nrf54l15 \
-s sample.ipc.icmsg.nrf54l15_no_multithreading \
-s sample.ipc.icmsg.nrf54l15_remote_no_multithreading \
-s sample.ipc.icbmsg.nrf54l15 \
-s sample.ipc.icbmsg.nrf54l15_remote_no_multithreading
```
I used nrf54L15DK (instead of hardware map, you can use `-p nrf54l15dk/nrf54l15/cpuapp --device-serial /dev/ttyACM1 --device-serial /dev/ttyACM0` ).
It can also be tested on nrf54H20 or nrf5340dk.
Afer execution, you'll find:
- logs from second core in the console
- a `handler_1.log` file in test output directory

To verify backward compatibility on native / QEMU:
```
$ZEPHYR_BASE/scripts/twister --no-clean  -vv -ll debug \
-p native_sim -p qemu_cortex_m3  \
-T $ZEPHYR_BASE/samples/subsys/testsuite/pytest/shell -s sample.pytest.shell
```

First, you are accessing a "private" variable from a `DeviceConnection` instance. Second, the `DeviceAdapter` should not be aware of the implementation details of the `DeviceConnection` class. With the current approach, any change in the `DeviceConnection` class will require an update to the `DeviceAdapter` as well (for example, if the name of the variable `_process` changes).

I would change this implementation to something like this:
```python
for conn in self.connections:
    conn.update(process=self._process)
```

And in the DeviceConnection class add `update` (or `init`) method with kwargs argument which can be a process instance for above case. 
```python
class DeviceConnection(ABC):
    ...
    def update(self, **kwargs):
         pass
````

*--- Copilot (2025-12-20 08:27:12+00:00)
The regex pattern for splitting serial_pty has changed from `',| '` (comma OR space) to `'[, ]'` (single character that is either comma OR space). This changes the behavior:

- Original: splits on comma or space, so `"cmd arg1,arg2"` becomes `["cmd", "arg1", "arg2"]`
- New: splits on each comma or space character individually, so `"cmd arg1,arg2"` becomes `["cmd", "", "arg1", "", "arg2"]` (with empty strings)

The new pattern will create empty strings in the result when consecutive delimiters are present. The original pattern was more robust.
```suggestion
                re.split(',| ', self.serial_config.serial_pty),
```

*--- Copilot (2025-12-20 08:27:12+00:00)
Missing `continue` statement after `time.sleep(0.05)`. In the original code flow, when `in_waiting == 0`, the loop should continue waiting. Without the `continue`, the code will fall through to the `else` block, which is incorrect logic. This could cause the thread to busy-loop or behave unexpectedly when no data is available.

*--- Copilot (2025-12-20 08:27:13+00:00)
The `is_device_connected()` method returns a truthy value but not necessarily a boolean. When `_serial_connection` is not None, it returns the result of `_serial_connection.is_open`, which is correct. However, when `_serial_connection` is None, this returns None (falsy) instead of False (boolean). While functionally equivalent in boolean context, this is inconsistent with the method's return type hint which specifies `bool`. Consider using `return bool(self._serial_connection and self._serial_connection.is_open)` for clarity and type safety.
```suggestion
        return bool(self._serial_connection and self._serial_connection.is_open)
```

*--- Copilot (2025-12-20 08:27:13+00:00)
The `readlines_until` method in DeviceAdapter doesn't ensure a default timeout is set when not provided in kwargs. Unlike the `readline` method (lines 105-106) which explicitly sets a default timeout, `readlines_until` directly passes kwargs to the connection's method. While the underlying DeviceConnection.readlines_until does handle None timeout (line 125), it's inconsistent with the pattern used in `readline` and may not match the documented behavior that states it "uses base_timeout if not provided".
```suggestion
        self.check_connection(connection_index)
        if kwargs.get('timeout') is None:
            kwargs['timeout'] = self.base_timeout
```

Not only from the command line, you can add second port (with the same `id`) in the hardware map: https://docs.zephyrproject.org/latest/develop/test/twister.html#multi-core-testing-support
