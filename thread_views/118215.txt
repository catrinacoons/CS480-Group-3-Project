*--- Copilot (2026-09-03 12:26:36+00:00)

*--- jhedberg (2026-09-08 12:53:13+00:00)
The `if` cannot make the write safe: the stack writes before the driver sees the return value, and for ACL/ISO the buffer it would write into is the host's `buf->data`, sized for the data it carried, while commands go through `hci_cmd_buf`, sized for a full event. A data-path response would have overrun the buffer before this block runs. What the guard buys is smaller: the driver never interprets a data-path return value as an event, and the code states the contract you just described, that only synchronous commands produce a response. If that contract changes, this function has to change anyway to route the data path through a response-sized buffer, so there is nothing to future-proof here. I would keep the guard with a comment stating the contract, but I won't block on one condition either way. The other inline question and the commit message are still open.

*--- Thalley (2026-09-11 06:58:37+00:00)
Outside the scope of this PR since it's just moved, but it's a bit confusing that this function uses `ret` for the return value, while the user of this function uses `err` as the return value. Those are not semantically identical, and it's somewhat odd to use `1` as an error compared to e.g. `-1`

*--- msmttchr (2026-09-11 08:57:55+00:00)
Indeed, the `BLECB_Indication` is a callback from ST Link layer and it returns value is an `uint8_t` as type with a convention that 0 is no error and any other value is an error. Since ST link layer uses positive numbers for errors, -1 could be odd, even though it will accomplish the target (see further).
The purpose of the return value is to inform the link layer that event has been processed (0) or not processed (any non-zero value). In the latter case, the ST link layer keeps the event in the internal queue to give another chance to process it at later time.
