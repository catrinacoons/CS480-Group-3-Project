TITLE: modem: cellular: on-demand GNSS power control

*--- opening post by papadkostas (2026-09-14 23:14:44+00:00)
This PR adds on-demand control of the GNSS receiver integrated in a cellular modem API

Integrated GNSS receivers are common in asset trackers, where power consumption is critical: the receiver should only run while the application needs a fix, and switching it on or off should not disturb the cellular link. The driver of the GNSS receiver is the owner of that decision, so this PR gives it an API to switch the receiver through the modem driver, at any point in the modem's lifecycle. First user of this is U-blox SARA-R4. Some fixes landed additionaly in `modem_cellular` as they were found while testing it on hardware.

## On-demand GNSS power control
  - Two new optional chat scripts in struct modem_cellular_config_scripts: 
    - `gnss_power_on` GNSS power on AT commands
    - `gnss_shutdown` GNSS shutdown AT commands
  - Two new functions added, `modem_cellular_gnss_power_on` and `modem_cellular_gnss_shutdown`. The caller blocks until the above mentionedscripts has run, at most `CONFIG_MODEM_CELLULAR_GNSS_REQUEST_TIMEOUT_S` (default 60 s).
  - A request runs from a new `RUN_GNSS_REQUEST_SCRIPT` state, entered from `WAIT_FOR_APN`, `AWAIT_DIAL`, `AWAIT_REGISTERED` or `REGISTERED` when no other script is running on the AT channel. The modem returns to the same state afterwards, so the cellular link, including a running PPP session, is not affected.
  - Events that arrive while the GNSS script runs, such as registration changes or the interface going up or down, are queued and handled once it completes.
  - A request made while the modem is suspended or still starting up waits until the modem reaches one of these states. 
  - Before the modem powers off, `gnss_shutdown` runs over the AT channel. The last known receiver state is tracked, so a script for the state the receiver is already in is not sent again.

For the SARA-R4, `CONFIG_MODEM_CELLULAR_U_BLOX_SARA_R4_GNSS` provides the scripts (`AT+UGPS=1,0,15` and `AT+UGPS=0`) and adds `AT+UGPRF=2` to the init script. It routes the GNSS data to a muxed virtual port and must be sent before CMUX is started.

Modems without these scripts are not affected: the API returns `-ENOTSUP` and the new state is never entered, however slight code and RAM memory increase is noticiable. Will take care of it after review. 

## Power management

  - **Child devices:** with `CONFIG_DEVICE_DEPS`, the modem refuses to suspend (`-EBUSY`) while one of its devicetree children is in use: a child under runtime PM that holds a usage reference, or any other child in
  `PM_DEVICE_STATE_ACTIVE`. Previously the modem powered off underneath it. The application now suspends the children, such as the GNSS receiver, before releasing the last modem reference. An asynchronous runtime suspend cannot  report the refusal, so this order matters.
  - **Suspend during PPP teardown:** a suspend arriving in `AWAIT_PPP_DEAD`, typically right after the interface is brought down, was dropped, so `pm_action()` waited for its 30 s timeout and the modem stayed powered. It is now
  handled once the PPP teardown has settled.

## Fixes

  - `cmd_pipe` was left pointing at DLCI2 after dialing, so power-off scripts ran on the PPP data channel instead of the AT channel.
  - The `+CME ERROR` abort match is extended to `"+CME ERROR: "`, so `argv[1]` holds only the error code.
  - `modem_chat_release()` now also cancels the script timeouts, so a script started right after releasing a running one no longer inherits its deadlines.

  ## Testing

**Setup:** custom board with an nRF5340 and a u-blox SARA-R422M10S. An out-of-tree u-blox GNSS driver on CMUX DLCI3 calls the new API from its own PM handling. This out-of-tree driver, I plan to share next month together with extra related functionality.

  | Scenario | Result |
  |---|---|
  | Start-up with the GNSS option | `AT+UGPRF=2` accepted before `AT+CMUX`. A power-on request made during the power pulse waits and runs from `AWAIT_DIAL`, `AT+UGPS=1,0,15` answers `OK` in about 1.2 s, the receiver initialises on DLCI3 and GNSS driver initializes and gets fixes. |
  | Receiver off/on while idle and connected | 5 cycles in `AWAIT_DIAL` and 6 in `REGISTERED` with PPP up: all `OK`, the link and the periodic script unaffected. |
  | Request while a periodic script runs | 18 requests at a 300 ms poll interval of which 4 that arrived during a poll started only after it completed. All completed. |
  | Request for the state the receiver is already in | Completes with no additional AT command sent. |
  | Interface brought up during a GNSS script | The dial waits for the script, then runs once. Link comes up. |
  | Suspend while a request waits or runs | From `REGISTERED` state, 50, 300 and 800 ms after the request: `-ECANCELED`. The running `AT+UGPS=1` completes before `AT+UGPS=0` and the power-off, and the next dial connects. During modem  start-up (3.5 and 4.4 s after resume): `-ECANCELED`, normal power-off. |
  | Request while the modem stays suspended | Waits, then `-ETIMEDOUT` after the configured timeout. No state change. |
  | Suspend while the GNSS receiver is in use | Refused with `-EBUSY` (`Refusing to suspend: child device ... is still in use`). The modem stays up. |
  | Interface down from a connected state, then suspend | The suspend arrives in `AWAIT_PPP_DEAD`, is handled when that state is left, and the modem reaches `IDLE` about 1.1 s later with a 10 s periodic interval. Before this change, `pm_action()` timed out after 30 s with the modem still on. |
  | Power-off with the receiver state known off | `gnss_shutdown` is skipped. |
  | Power-off with the receiver state unknown | `AT+UGPS=0` is sent, the module is either responding with OK or refuse with`+CME ERROR: 1799` aborting the script at once, and the power-off continues normally. |
  | Cycle tests | 50 cycles of receiver off, interface down, suspend, resume, interface up, receiver on: 50/50, no script failures, no dropped events. |

Built with `tests/drivers/build_all/modem` on native_sim, also with `CONFIG_GNSS=y` and `CONFIG_MODEM_CELLULAR_U_BLOX_SARA_R4_GNSS=y`.

Only the SARA-R4 has been tested. The mechanism is generic and could be applied to other cellular modems that attach the GNSS receiver on MUX, regardless if they have user pipe available or not. All it needs is its own `gnss_power_on` and `gnss_shutdown` scripts. Feedback from anyone with such hardware is welcome.

The main issue with doing this entirely from the GNSS driver is that the SARA-R4 variant I am currently working with does not provide a user pipe for GNSS. The GNSS commands therefore have to go through the cellular modem driver's command path.

For modems that provide a dedicated user pipe, implementing GNSS as a separate driver that owns the GNSS communication makes perfect sense. However, I don't think we should make the presence of a user pipe a requirement for the GNSS subsystem, since that would prevent modems without one from using the same subsystem architecture.

I agree with the broader point, though that the GNSS subsystem should ideally have ownership of requesting GNSS functionality, but the modem driver should provide the transport/control mechanism required by the particular modem. I'll look into how we can structure this so that the GNSS subsystem is responsible for enabling/disabling GNSS and the modem-specific implementation can handle cases such as the SARA-R4, where there is no separate GNSS user pipe.

The current implementation came from a somewhat different goal. I was initially focused on enabling GNSS as early as possible during modem startup to achieve the best possible TTFF, rather than designing the GNSS functionality around the subsystem's ownership and PM model. I'm going to rework this PR.

As far as I can see, one case I don't see covered in the PR or the discussion so far: modems where GNSS and LTE share the RF path and are mutually exclusive. On the HL78xx, GNSS can only be used when the module is not actively connected on LTE/GSM. That makes two things hard to use on this class of modem:

- GNSS is running and the app calls net_if_up(): does the modem driver run the GNSS shutdown first, or refuse?
- Could the vendor config carry a flag (e.g. "GNSS and LTE are exclusive") so the core driver knows whether a GNSS request is legal in REGISTERED or requires the not-registered state?

*--- papadkostas (2026-09-17 23:26:52+00:00)
@zafersn thanks for the detailed look and good context on a case such as for HL7800/HL7812.

HL78xx is architecturally a different case and it already has its own standalone driver in-tree that's built for exactly that. I don't think its a good idea to mix this here :worried:

For CMUX-based modems with integrated GNSS, I'd argue RF path prioritization stays an application concern rather than something the driver arbitrates. The driver already treats GNSS power and network connectivity as two independently controlled things: 
- on-demand GNSS power on/shutdown or start/stop
- net up/down (with ON_DEMAND_CONNECT holding the modem "up but not dialed" until the app asks).
 
On shared-RF variants, the app should just bring the interface down, wait for it to settle, then request GNSS, shut GNSS down or just stop, before bringing the interface back up. Baking that sequencing into the driver would mean it silently deciding to preempt one side or the other, which seems like the wrong owner for that call.

What we don't have ye is bringing the interface down parks the modem at AWAIT_DIAL but never touches CFUN and the radio stays fully functional and registered the whole time, so on shared-antenna hardware GNSS still wouldn't get a clear RF path. The missing piece isn't GNSS-aware arbitration in the driver, it's exposing CFUN/low-power control to the application at all. Right now it's hardcoded into the init/dial scripts with no application hook. That would be a small, generic addition, not GNSS-specific, and the app would still own the actual policy, which is where I think it belongs.

I think the key 'problem' to solve here is splitting out the modem base functionality (booting, setting up CMUX) from the higher level functionalities (PPP/GNSS). Right now `modem_cellular` is making the assuming that a PM request is a request for PPP connectivity. This is driven from the `modem_ppp` file:
https://github.com/zephyrproject-rtos/zephyr/blob/52b48529aecc3ad0ef9b159996bdb5d2b3e5b794/subsys/modem/modem_ppp.c#L552-L561

Any solution which can handle GNSS as a mutually exclusive operation will need to break this assumption. `pm_device_runtime_get` should be a necessary pre-condition for the PPP interface, but it shouldn't be the only API call required. Something along the lines of:
