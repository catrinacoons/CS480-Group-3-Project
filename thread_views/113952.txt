*--- Copilot (2026-08-14 09:42:24+00:00)
`writer` is a pointer member of `smp_streamer`, not an embedded object, so applying `CONTAINER_OF` to the address of this local pointer produces a bogus stack address. Invalid-mode handlers call this path and can crash while resetting the response. Reset the recovered writer directly (or change the callback API to pass the streamer).

*--- Copilot (2026-08-14 09:42:24+00:00)
The advertised custom group-ID modes never take effect because the group is always registered as ID 11. Assign `transport_mgmt_group_id()` before registration so both the Kconfig value and runtime callback select the actual registered group.

*--- Copilot (2026-08-14 09:42:25+00:00)
Custom group IDs are also bypassed in error responses: every `smp_add_cmd_err()` here and in the new transport callbacks tags the error with the default ID 11. Once custom registration is fixed, clients will receive an `err.group` that does not match the command group. Use `transport_mgmt_group_id()` consistently across all these call sites.

*--- Copilot (2026-08-14 09:42:25+00:00)
With `MAX_BRIDGES > 1`, this only searches for a free slot and allows the same incoming or outgoing endpoint to be connected repeatedly. Forwarding and disconnect lookup return only the first matching slot, leaving later bridges unreachable or routing to an older target. Reject a connect when either endpoint is already bridged in the requested direction, or redesign lookup to disambiguate multiple peers.

*--- Copilot (2026-08-14 09:42:25+00:00)
The protocol says `transport` and `all` must not both be present, but this rejects them only when `all` decodes to true. A request containing both fields with `"all": false` is accepted and disconnects the named transport. Check field presence regardless of the boolean value.

*--- Copilot (2026-08-14 09:42:25+00:00)
If any bridge is active but the requested transport is not part of one, the helper returns success and this command emits an empty success response. Return `TRANSPORT_MGMT_ERR_NOT_BRIDGED` when no matching bridge is found so a request cannot silently do nothing.

*--- Copilot (2026-08-14 09:42:25+00:00)
Bridge state can change between `transport_mgmt_is_bridged()` and `transport_mgmt_get_bridge()`, and the latter releases its lock before returning. A concurrent disconnect can therefore make `bridge` NULL or clear its transport pointer before the dereference. Provide an atomic lookup/use operation or hold a lifetime-protecting lock/reference through transmission.

*--- Copilot (2026-08-14 09:42:26+00:00)
The same lookup/use race exists for bridged responses: a concurrent disconnect can clear this static bridge after lookup and before `incoming_transport` is dereferenced. Protect bridge lifetime through the output call rather than returning an unlocked mutable pointer.

*--- Copilot (2026-08-14 09:42:26+00:00)
`req->len` still includes every subsequent SMP message in the input buffer, so passing a reference here sends the whole remainder on the first bridge output. The loop then advances and sends later messages again. Forward a buffer view/copy limited to exactly `sizeof(struct smp_hdr) + req_hdr.nh_len`.

*--- Copilot (2026-08-14 09:42:26+00:00)
This response path also forwards the entire remaining input buffer rather than the current SMP frame, duplicating concatenated responses when the loop reaches them. Pass a frame-limited buffer of header plus `nh_len` bytes.

*--- Copilot (2026-08-14 09:42:26+00:00)
The result of both CBOR encodes is discarded and this callback reports success even when the response buffer is exhausted, producing a truncated `configs` response. Propagate `ok` and set `rc` as the other bridge-info callbacks do.

*--- Copilot (2026-08-14 09:42:27+00:00)

*--- Copilot (2026-08-18 10:23:21+00:00)

*--- thedjnK (2026-08-19 12:41:27+00:00)
you do need to pass the direction, you can bridge a transport twice (in theory) e.g. a UART can be bridge to bluetooth so read/write requests going into UART go out of bluetooth, and then read/write responses from bluetooth go back to the UART. But you can also bridge UDP to the UART so read/write requests coming in on UDP go out via the UART, then read/write responses coming in on the UART go to UDP. I don't know if such a system is something anyone would want but fundamentally it is supported. The "other" here is the transport is it bridged to **in that specific direction**, so if you put UART in and set direction to incoming, you'd get the bluetooth transport back, if you put UART in and set direction to outgoing, you'd get the UDP transport back
