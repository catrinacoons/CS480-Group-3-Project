TITLE: Bluetooth: Kconfig: Only restrict system workqueue priority when needed

*--- opening post by waihongtam (2026-09-15 03:52:32+00:00)
Enabling `CONFIG_BT` restricts `SYSTEM_WORKQUEUE_PRIORITY` to the cooperative
range for every build, but the requirement comes from the individual
components that submit work to the system workqueue, not from Bluetooth being
enabled. This adds a hidden `BT_SYSTEM_WORKQUEUE_COOP` symbol and applies the
range only when one of those components is enabled. See the commit message for
the reasoning.

Motivated by an out-of-tree application that drives an external controller and
deliberately runs the system workqueue as its lowest-priority thread, so that
the watchdog it services is only fed while the whole system is still making
progress. Today that application cannot enable `CONFIG_BT` at all.

### Testing

Built against `main` with Zephyr SDK 1.0.1.

| Configuration | Board | `BT_HCI_RAW` | `BT_CTLR_PRIVACY` | `BT_SYSTEM_WORKQUEUE_COOP` | `SYSTEM_WORKQUEUE_PRIORITY` |
| :--- | :--- | :-: | :-: | :-: | :-: |
| `samples/bluetooth/hci_uart_3wire` | nrf52840dk/nrf52840 | y | y | y | -1 |
| `samples/bluetooth/hci_uart` | nrf52840dk/nrf52840 | y | y | y | -1 |
| `samples/bluetooth/peripheral` | nrf52840dk/nrf52840 | n | y | y | -1 |
| minimal app, `BT_HCI_RAW=y` + userchan, asking for `SYSTEM_WORKQUEUE_PRIORITY=10` | native_sim | y | n | **n** | **10** |

The first three are unaffected by this patch; note that two of them are
`BT_HCI_RAW` builds that still require the cooperative range, which they get
through `BT_CTLR_PRIVACY`. The fourth is the case being addressed.
