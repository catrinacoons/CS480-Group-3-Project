TITLE: drivers: pcie: Introducing CONFIG_PCIE_HOST

*--- opening post by soburi (2026-05-31 00:46:39+00:00)
The file `drivers/pcie/host/pcie.c` is compiled if `CONFIG_PCIE`
is enabled, but it depends on the actual PCIe controller,
and a contradiction occurs when the sub-option `CONFIG_PCIE_CONTROLLER`
is set to `n`.

To resolve this, we introduce `CONFIG_PCIE_HOST`.

CONFIG_PCIE_HOST defaults to y when CONFIG_PCIE_CONTROLLER or X86 is
enabled, and it controls compilation of the files under drivers/pcie/host/.
Endpoint-only configurations can enable CONFIG_PCIE without pulling in the
host support.

*--- Copilot (2026-05-31 10:15:57+00:00)
Multiple in-tree drivers (e.g. `drivers/ethernet/Kconfig.e1000`, `drivers/can/Kconfig.kvaser`, `drivers/smbus/Kconfig` SMBUS_INTEL_PCH, `drivers/virtio/Kconfig` VIRTIO_PCI) only `select PCIE` but rely on the host-side APIs (`DEVICE_PCIE_DECLARE`, `pcie_conf_read`, `pcie_get_mbar`, etc.) implemented in `drivers/pcie/host/pcie.c`. After this reorganization, `select PCIE` no longer pulls in those APIs; host support is only enabled when `PCIE_HOST` is set, which here only defaults `y` if `PCIE_CONTROLLER || X86`.

For in-tree boards this is mostly covered (x86 targets get `PCIE_HOST=y` by default, and controller-based ARM/RISC-V boards set `PCIE_CONTROLLER`), but the contract of `select PCIE` has silently changed: out-of-tree boards (or future in-tree non-x86, non-controller hosts) that enable e.g. `ETH_E1000` will now build with `CONFIG_PCIE=y` but `CONFIG_PCIE_HOST=n` and fail to link the host APIs. Consider either having these drivers also `select PCIE_HOST`, or making `PCIE_HOST` default `y` whenever `PCIE` is enabled and let endpoint-only configs explicitly disable it.
