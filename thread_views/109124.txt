## Summary

Add a pytest-based functional test for the Bluetooth Classic HID Device profile, using Bumble as the HID Host counterpart. This follows the same pattern as existing classic BT tests (`a2dp_sink`, `a2dp_source`, `rfcomm_c`, etc.).

- DUT application (`test_hid_device.c`) provides shell commands for HID Device operations: register, connect, disconnect, reconnect, send report, virtual cable unplug
- Pytest (`test_hid.py`) uses `bumble.hid.Host` to exercise the full HID protocol over L2CAP control (PSM 0x0011) and interrupt (PSM 0x0013) channels

## Test Cases (8 total)

| # | Test | Description |
|---|------|-------------|
| 1 | `test_hid_case_register` | Register HID callbacks + SDP record |
| 2 | `test_hid_case_connect_host_initiated` | Bumble Host opens L2CAP ctrl+intr → HID connected/disconnected |
| 3 | `test_hid_case_get_report` | Valid report_id → DATA response; invalid id → ERR_INVALID_REPORT_ID |
| 4 | `test_hid_case_set_report` | Valid → HANDSHAKE SUCCESS; invalid → ERR_INVALID_REPORT_ID |
| 5 | `test_hid_case_protocol` | GET_PROTOCOL + SET_PROTOCOL (boot/report mode) |
| 6 | `test_hid_case_send_input_report` | DUT sends input report → Bumble receives on interrupt channel |
| 7 | `test_hid_case_suspend_resume` | Host sends SUSPEND/EXIT_SUSPEND → DUT callback fires |
| 8 | `test_hid_case_virtual_cable_unplug` | DUT sends VCU → Bumble receives notification |

## Dependencies

This PR depends on #94012 (HID Device profile) being merged first. The test uses the `bt_hid_device_*` API and `CONFIG_BT_HID_DEVICE` Kconfig introduced there.

`asyncio.get_event_loop()` is deprecated and produces DeprecationWarnings on Python 3.10+ and is scheduled for removal. Inside a running coroutine (which is the case here since these are `async def` functions awaited via `asyncio.run`), use `asyncio.get_running_loop()` instead, or simply construct the future via `loop = asyncio.get_running_loop(); loop.create_future()` once at the top of the coroutine. This affects all 9 occurrences (lines 222, 239, 301, 318, 376, 388, 402, 459, 569).

This issue also appears on line 317 of the same file.

*--- Copilot (2026-05-14 07:36:31+00:00)
In `hid_case_virtual_cable_unplug`, the DUT command is issued via `shell.exec_command("hid_dev vcu")` directly, while every other test uses the `send_cmd_to_iut(...)` helper that asserts a successful response. This bypasses the consistent error-handling pattern and provides no verification that the command actually executed successfully on the DUT. Use `send_cmd_to_iut(shell, dut, "hid_dev vcu", None)` (or with a parse string) for consistency.

*--- Copilot (2026-05-14 07:36:31+00:00)
After the VCU completes, the test never calls `bumble_acl_disconnect(...)`. Other tests cleanly tear down the ACL connection at the end. Leaving a stale ACL state across tests in the same pytest session (which uses `pytest_dut_scope: session`) can cause subsequent test cases to fail or behave unpredictably since the DUT may still consider itself paired/connected.

*--- Copilot (2026-05-14 07:36:31+00:00)
`device_power_on` swallows every exception in an unbounded retry loop. If `power_on()` fails for a non-transient reason (e.g., bad HCI transport, permission error), this will spin indefinitely and the test will only fail by hitting the 180s testcase timeout, with no useful diagnostic. Bound the retry count and/or log the exception, and re-raise after N attempts.

*--- Copilot (2026-05-14 07:36:31+00:00)
`hid_set_report_cb` reads `buf->len` for logging but does not consume the data with `net_buf_pull_*` or unref it. Whether the caller (`bt_hid_device`) owns the buf after the callback returns is API-contract-dependent; please verify against the `bt_hid_device` set_report callback contract introduced in PR #94012. If callers are expected to consume payload via `net_buf_pull*`, add it; if buf ownership transfers on a non-zero return, the early -ENOENT path may leak/double-free the buffer.

*--- Copilot (2026-05-14 07:36:32+00:00)
`hid_get_report_cb`/`cmd_send` directly access `hid->boot_mode`, treating the `bt_hid_device` struct as if it has a public layout. Public APIs in Zephyr's Bluetooth stack typically expose accessors (e.g., `bt_hid_device_get_protocol_mode()`); accessing internal struct members from a test app couples the test to private implementation details and will break if the struct is reorganized. Confirm whether `boot_mode` is part of the documented public API or add an accessor.

*--- Copilot (2026-05-14 07:36:32+00:00)
`hid_pool` is sized for only 2 buffers but is shared between the asynchronous response path in `hid_get_report_cb` and the explicit input report path in `cmd_send`. With back-to-back GET_REPORT/SET_REPORT/SEND traffic, the pool can deplete and `bt_hid_device_create_pdu()` will return NULL, causing tests to fail intermittently. Consider increasing the count to at least 4–8 to provide headroom under realistic test traffic.

*--- Copilot (2026-05-14 07:36:33+00:00)
