TITLE: Bluetooth: Classic: HFP: CLCC report NULL when finish

*--- opening post by expliyh (2025-12-24 13:09:39+00:00)
The CLCC API does not report when it finishes, so the app cannot
determine whether the CLCC procedure has ended. This commit modifies the
behavior of the CLCC API to call the callback with a NULL Call pointer to
indicate that the CLCC procedure has completed.

*--- lylezhu2012 (2026-01-05 07:34:00+00:00)
> A timeout is not really reasonable. A worst case (typically during sniff) can cost several seconds. Let's say a 3 seconds timeout (not even enough). 

Indefinite waiting is unreasonable. Just like you said, 3 seconds might not be enough. That would be reasonable if there were a worst-case waiting time. 
So, I think the timeout is necessary for application. It is used to ensure the action can be done in limited time from application's perspective. 

> This means that an application can not do any other action (because the previous AT transaction is not completed) during this 3 seconds.

From the perspective of the HFP HF API, there is no restriction that the next API can only be called after the previous API has been executed. All AT commands are queued and all of them will be executed one by one internally.

So, unless the next AT command depends on the return value of AT+CLCC, the app can call any interfaces.
