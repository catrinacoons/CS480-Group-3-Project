TITLE: [RFC] Driver: pwm: add batch capture api

*--- opening post by juickar (2026-07-06 16:18:32+00:00)
The goal of this PR is to introduce a new API to do batch capture of a PWM signal.
The existing PWM capture API reports one sample per callback, which increases interrupt overhead at higher frequencies
This new API lets drivers pass buffers and use DMA-based capture, so they can return one batch of samples and reduce callback overhead.

*--- Copilot (2026-07-10 09:02:06+00:00)
The Kconfig help says the DMA buffer size is the number of samples per completion callback, but the STM32 implementation invokes the batch callback with CONFIG_PWM_CAPTURE_DMA_BUFFER_SIZE/2 samples (half-buffer) per event. This is user-visible and will cause confusion when sizing buffers.

*--- Copilot (2026-07-10 09:02:07+00:00)
The pwm_configure_capture_batch() documentation states the callback is invoked with a full buffer on each DMA completion, but the STM32 driver calls the callback on both half- and full-buffer events and passes a half-buffer count. Please update the doc to match the API behavior (or vice-versa).

*--- Copilot (2026-07-10 09:02:07+00:00)
dma_cfg enables half/complete callbacks even when notify=false (secondary DMA stream). On many DMA drivers this still enables HT/TC interrupts, increasing interrupt load and undermining the point of batch capture. Gate the callback-enable flags on notify so only the primary stream generates DMA interrupts.

*--- Copilot (2026-07-10 09:02:07+00:00)
CAPTURE_INIT has excessive spacing and would be clearer (and less error-prone for future edits) if formatted like the other init macros with consistent indentation and line wrapping.

*--- Copilot (2026-07-10 09:02:07+00:00)
pwm_get_cycles_per_sec() returns an error code; ignoring it can leave cyc_per_sec uninitialized and later division (cyc_per_sec / avg_period) becomes unreliable. Handle the return value and fail early on error.

*--- Copilot (2026-07-10 09:02:08+00:00)
The README sample output text doesn't match what the code prints (it shows "avg: frequency" but the sample prints "avg frequency"). Keeping them aligned helps users verify expected output.

*--- jsbatch (2026-07-16 18:19:59+00:00)
Rather than using a statically allocated buffer in the driver, as demonstrated by pwm_stm32.c:102, what about having the batch capture buffer be application owned.  Modeled similar to the ADC, this might look something like this:

```
struct pwm_capture_batch {
        uint32_t channel;
        pwm_flags_t flags;
        uint32_t *period_buf;
        uint32_t *pulse_buf;
        size_t    buf_len_samples;
        pwm_capture_batch_callback_handler_t callback;
        void *user_data;
};

/* entry point mirrors adc_read() */
typedef int (*pwm_configure_capture_batch_t)(const struct device *dev,
                                             const struct pwm_capture_batch *seq);
```

Another thought that comes to mind, should the API provide for double buffering instead?  Since we don't know exactly when the next capture will come in continuous mode, that could help mitigate overruns.
