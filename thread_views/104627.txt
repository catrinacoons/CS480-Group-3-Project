TITLE: Bluetooth: CAP: Make CAP cancel thread safe

*--- opening post by Thalley (2026-02-26 20:11:19+00:00)
The functions bt_cap_commander_cancel and
bt_cap_initiator_unicast_audio_cancel were not thread safe, and calling these while handling e.g. a notifications or a write response could cause fatal errors.

This commit modifies active_proc so that all access to it is guarded by a mutex.

Fixes https://github.com/zephyrproject-rtos/zephyr/issues/104273

*--- Copilot (2026-02-26 20:45:26+00:00)
bt_cap_common_clear_proc() unlocks `active_proc_mutex` before clearing the struct. That reintroduces a race where another thread can read/modify `active_proc` while it is being memset, and it also mixes non-atomic writes with atomic reads of `proc_state_flags`. Clear the procedure while still holding the mutex (and preferably clear `proc_state_flags` via atomic operations), then unlock afterwards.
```suggestion
	/* Clear state flags atomically before clearing the rest of the struct */
	(void)atomic_clear(&proc->proc_state_flags);

	(void)memset(proc, 0, sizeof(*proc));

	bt_cap_common_unlock_proc(proc);
```

*--- Copilot (2026-02-27 12:53:24+00:00)
bt_cap_common_get_active_proc() asserts on k_mutex_lock() failure but does not otherwise handle non-zero return codes. In builds where __ASSERT is disabled, a timeout (-EAGAIN) would still return a pointer even though the mutex was not taken, reintroducing data races. Consider using K_FOREVER for the lock, or change the API to propagate lock failures (e.g., return NULL / error code) so callers can avoid accessing active_proc without the mutex.

bt_cap_common_clear_proc() asserts that active_proc_mutex.lock_count == 1, but the mutex is recursive and there are call paths that re-lock it (e.g., a callback holds the lock and calls another helper that calls bt_cap_common_get_active_proc() again).
