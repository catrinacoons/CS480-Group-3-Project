TITLE: modem: pipe: support dual transmit buffers

*--- opening post by JordanYates (2026-05-19 01:57:39+00:00)
Rework of #98541 to address compatibility feedback.
The existing function `modem_pipe_transmit` continues to work as it does now, regardless of backend support for `transmit_double`.
The new function `modem_pipe_transmit_double` works regardless of backend support for `transmit_double`.

Handle sending the request and delimiter strings in a single call to the pipe backend. This has two advantages:
     1. No time gap between request and delimiter on the interface (more efficient line utilization)
     2. Fewer bytes transmitted on the line for pipes that perform wrapping (CMUX).

For example, sending "ATE0" + "\n" through CMUX now takes 11 bytes, instead of the previous 17 bytes (10 + 7):
```
[00:00:38.268,064] <wrn> modem_cmux: TX
                                     f9 0b ef 0b 41 54 45 30  0d 5d f9                |....ATE0 .].
```

The double buffer send functionality is exposed through a new function in the modem pipe API, meaning all existing code does not require any changes.

*--- Copilot (2026-05-19 13:49:56+00:00)
In the ISR UART backend, extra_buf is queued even if ring_buf_put() couldn't enqueue the full primary buffer. That can interleave delimiter bytes before the remaining request bytes, breaking the required byte ordering for transmit_double. Only enqueue extra_buf when written == size (or compute available space up front so buf is fully enqueued before any extra).

*--- JordanYates (2026-05-20 03:18:13+00:00)
Because both "buffers" in the context of `modem_chat` are ROM constant strings. There is no intermediary buffer in the module, and adding one would impose:
 1. RAM overhead, and questions around how large the buffer should be given the required size in the `modem_chat` instance would depend on the scripts that are being run
 2. Runtime overhead, copying both ROM strings into a RAM buffer to pass off to a backend, which often does its own copy into a RAM buffer.

*--- bjarki-andreasen (2026-06-11 14:38:15+00:00)
> So I want to be very clear on this before I implement this feature for the third time, because the consequences of your suggestions just lead back to the reasons the first attempt in #98541 was rejected.

I think breaking the API in this case will result in a more efficient and scalable solution, at quite little cost to users of pipes, and implementers of backends:

Given we are modifying the API to bring efficiency enhancements, not functional ones, we can add thin wrappers on both the user and backend sides of the pipe transmit APIs:
```
static int pipe_call_transmit_chain(struct modem_pipe *pipe,
                                    const struct modem_pipe_fragment *fragments,                            
                                    size_t fragments_size)
{
        int ret;
        int transmitted;

        if (pipe->api->transmit_chain == NULL) {
                for (size_t i = 0; i < fragments_size; i++) {
                        ret = pipe->api->transmit(pipe->data, fragments[i].data, fragments[i].size);
                        if (ret <= 0) {
                                return ret;
                        }

                        transmitted += ret;
                };

                return transmitted;
        }

	return pipe->api->transmit_chain(pipe->data, fragments, fragments_size);
}
```
which would compliment the thin wrapper for `modem_pipe_transmit` below. We could then deprecate the transmit API over a release.

*--- wkhadgar (2026-06-11 18:50:37+00:00)
+1 to the chain + fallback direction. The fallback wrapper is the part that makes it work: a backend that only implements transmit keeps running unchanged, so this isn't a repeat of the out-of-tree break from #98541, the backend hook stays functional, and only the user-facing surface soft-deprecates.

To be fair to the double approach though: every current consumer is effectively 2 regions (chat request + delimiter), and double serves all of them. I went looking for an in-tree case that needs more, parameterized commands like `cellular_set_apn()` get `snprintk`'d into a single buffer before they reach the pipe, so they're 2 blocks too, not N. So there's no live N>2 caller today that double can't handle, at least not that I can think of right now...

Where I still lean on chain is future-proofing: it can be non-breaking via the fallback, and it means we don't re-break the API the day a caller wants to hand over fragmented sources. It's somewhat more to implement than double, mostly in the partial-write resume (cursor into a fragment array vs two fixed regions), so it's not free, just a one-time cost that buys not having to touch the API signature again. That's a preference, not a concrete gap double leaves open today, if it's not worth that cost, double is a fine place to land.

Either way happy to help review.
