*--- opening post by alxelax (2026-09-16 09:49:52+00:00)
The replay protection list and the solicitation replay list shared the
pending-store work item with every other settings flag. Scheduling any
other flag, such as model data, rescheduled that work item to
CONFIG_BT_MESH_STORE_TIMEOUT, and the handler then stored every flag
that was set, the replay lists included. CONFIG_BT_MESH_RPL_STORE_TIMEOUT
was therefore only honored while nothing else was pending, and the
replay lists were written to flash far more often than configured.

Give the replay lists a work item of their own, armed with
CONFIG_BT_MESH_RPL_STORE_TIMEOUT. store_pending_flags() now takes a mask
so that each work item stores only the flags it owns, and the generic
item masks the replay list flags out. bt_mesh_settings_store_pending()
cancels both items and flushes everything, leaving the synchronous path
unchanged. Both replay lists keep sharing one deadline, and each is
still stored only when its own flag is set.

plus unit tests to check that there is no interference among stored groups and
all groups behave as designed.

There seems to be one side-effect with the new logic now. Old logic (due to bug) was saving RPL after IV update reset clears the RPL. So, When NO_WAIT_PENDING_BITS are triggered (specially for IV_PENDING), rpl_pending_store should be called.
