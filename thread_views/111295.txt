*--- rlubos (2026-06-15 13:50:24+00:00)
I think this will need some more complex fix, the issue is we're still modifying the orignal pkt hop_limit in the header, plus this function uses shallow clone, so the orignal pkt and the new one share the same buffer. And also if we decrement the orignal header's hop_limit in the loop, it may happen several times in case of multiple interface.

I'd suggest to:
* keep the original decrement above,
* use `net_pkt_clone()` instead of `net_pkt_shallow_clone()`, so that the cloned packet get it's own buffer, with already decremented hop_limit value in the IP header.
* and then restore the hop_limit in the original packet for further processing after the loop.

*--- Copilot (2026-06-15 13:56:43+00:00)
`net_pkt_set_ipv6_hop_limit()` only updates the net_pkt metadata; it does not modify the IPv6 header in the packet buffer. With the current `net_pkt_shallow_clone()` usage, forwarded multicast packets will keep the original on-wire hop limit (no decrement). To actually decrement hop limit only for forwarded packets, clone the packet buffer (deep clone) and update `NET_IPV6_HDR(pkt_cpy)->hop_limit` before sending.
