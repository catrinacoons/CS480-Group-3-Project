TITLE: net: route: fix IPv6 ping from AIL host to Thread device

*--- opening post by jysalaun (2026-09-08 13:32:19+00:00)
Without this fix, a simple IPv6 ping from a host on an adjacent link
    (e.g. the AIL) to a device reachable via a different egress interface
    fails: when the next hop is not yet in the neighbor cache,
    net_route_ipv6_packet() returned -ENOENT and the packet (for a ping,
    the ICMPv6 Echo Reply) was dropped by the router.
    
    Instead of dropping it, clear the link-layer destination the packet was
    received with. net_send_data() then re-enters net_ipv6_prepare_for_send(),
    which already solicits the next hop and queues the packet until the
    Neighbor Advertisement arrives, reusing the existing forwarding path
    (hop-limit decrement, egress interface selection, NULL NS source address
    when forwarding). This mirrors the unknown-neighbor handling already used
    for locally-originated packets. When CONFIG_NET_IPV6_ND is disabled the
    previous -ENOENT behavior is kept.
    
    Add a regression test (net.route.ipv6.forward_nd): forward a packet to an
    unresolved next hop on an Ethernet interface, verify one NS is sent and
    the packet is queued, then resolve the neighbor and verify the queued
    packet is transmitted on the outbound interface.

*--- Copilot (2026-09-10 14:40:50+00:00)
Use `STALE` here. `net_ipv6_nbr_add()` initializes a directly-added `REACHABLE` entry with no reachable timer, while cache pressure evicts only `STALE` entries. With the default eight-entry cache, packets from eight distinct (or spoofed) global source addresses permanently fill the table and later AIL senders cannot be learned. A `STALE` entry still supplies the cached MAC for the first reply and then starts normal NUD.

*--- rlubos (2026-09-10 15:27:21+00:00)
I don't think this is the right direction, Border Router shouldn't be needed to do any workarounds for Thread->Ethernet forwarding to work, I've consulted with LLM as  I suspected there might be some bug in the generic routing code, and it confirmed my suspicion:

> When the Thread device's Echo Reply is forwarded toward the AIL host, the forwarding
transmit path does **not** perform neighbor discovery for the next hop:

```c
/* subsys/net/ip/route_ipv6.c, net_route_ipv6_packet() */
nbr = net_ipv6_nbr_lookup(NULL, nexthop);
if (nbr == NULL) {
    if (net_route_ll_addr_supported(out_iface)) {
        NET_DBG("Cannot find %s neighbor", ...);
        return -ENOENT;   /* <-- packet dropped, no NS ever sent */
    }
}
```

So it looks that the routing code would need updating to support neighbor discovery (the same way as locally originated traffic does) to make things work. I'd suggest going that way, especially that the current propsal has some other issues:

1. Only works for bi-directional traffic, packets originating from Thread interface still won't get neighbor entry.
2. Neighbor entries added in such way will never expire as reachable timer is set up via NS/NA processing.
3. The above would lead to eventual neighbor cache starvation.
4. And finally it kind of violates RFC 4861, which states that neighbor cache entries should only be populated by ND traffic, and even with that, unsolicted NS packets are only allowed to add STALE entries, never REACHABLE.
