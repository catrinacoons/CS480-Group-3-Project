TITLE: Bluetooth: Host: Fix bt_addr_le_is_resolved() matching non-identity types

*--- opening post by jhedberg (2026-09-15 18:28:17+00:00)
`bt_addr_le_is_resolved()` tests bit 1 of the HCI address type, which is also set for the anonymous advertiser (0xff) and unresolved directed address (0xfe) sentinels of the LE Extended Advertising Report event. Since the helper replaced the explicit identity-type comparison in `le_adv_recv()` (commit baad0c300fc0, 2023), the anonymous branch there has been unreachable: reports from anonymous advertisers reach scan callbacks with an address of type 0xfd instead of `BT_ADDR_LE_ANY`, which is what `bt_le_scan_recv_info` documents.

The fix compares against the two identity types explicitly. A ZTEST suite for `bt_addr_le_is_resolved()` and `bt_addr_le_copy_resolved()` is added to `tests/bluetooth/addr`.

Found while reviewing the resolved-address log annotation in #110687. That PR's `scan.c` log site does the same explicit comparison for now and can go back to the helper once this is merged. Both PRs add a source file to `tests/bluetooth/addr/CMakeLists.txt`, so whichever merges second needs a trivial rebase.

Verification: `tests/bluetooth/addr` on native_sim, 36/36 pass. No reproducer on hardware or bsim for the anonymous-advertiser path.

Please update that documentation to state that only `BT_ADDR_LE_PUBLIC_ID` and `BT_ADDR_LE_RANDOM_ID` return true and that the unresolved/anonymous sentinels return false.
