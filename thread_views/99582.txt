The `hal_radio_tx_power_value()` function is missing a case for +3 dBm. When `tx_power_lvl` is 3, it will match the condition `if (tx_power_lvl >= 0)` and incorrectly return `RADIO_TXPOWER_TXPOWER_0dBm` instead of `RADIO_TXPOWER_TXPOWER_Pos3dBm`. This needs to be added as a separate case before the >= 0 check:
```c
if (tx_power_lvl >= 3) {
    return RADIO_TXPOWER_TXPOWER_Pos3dBm;
}
```
```suggestion
	if (tx_power_lvl >= 3) {
		return RADIO_TXPOWER_TXPOWER_Pos3dBm;
	}
	if (tx_power_lvl >= 0) {
		return RADIO_TXPOWER_TXPOWER_0dBm;
	}
```

*--- Thalley (2025-11-28 10:21:49+00:00)
I wondered if there was a smarter way to implement these functions. Asked Copilot and got 

```c
static inline int8_t hal_radio_tx_power_floor(int8_t tx_power_lvl)
{
    /* Allowed TX power levels in descending order. Keep the -40 sentinel last. */
    static const int8_t levels[] = {8, 7, 6, 5, 4, 3, 2, 0, -4, -8, -12, -16, -20, -40};
    const size_t n = sizeof(levels) / sizeof(levels[0]);

    for (size_t i = 0; i < n; ++i) {
        if (tx_power_lvl >= levels[i]) {
            return levels[i];
        }
    }

    /* Should never get here because -40 is last, but return a fallback to be safe. */
    return levels[n - 1];
}
```

In number of lines it's certainly short, and it does avoid duplication of values, e.g. 

```c
	if (tx_power_lvl >= 7) {
		return 7;
	}
```

Is slightly more error prone if the 2 literal value are not the same. 

I'm OK either way, and I'm not sure about the sideeffects w.r.t. performance and code size
