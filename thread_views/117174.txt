TITLE: tests: net: dhcpv4: add a libFuzzer harness for the server receive path

*--- opening post by TheArkadiuszGrzelka (2026-08-23 18:19:11+00:00)
A DHCPv4 client has no address yet, so nothing authenticated it: every byte the server decodes is chosen by whoever sends a datagram to port 67.

The harness registers a dummy interface the way `tests/net/dhcpv4/server` does and injects a full IPv4 + UDP + DHCP packet, so the fuzzed path includes the socket read in the server's own callback.

The case runs on a Zephyr thread, following `samples/subsys/debug/fuzz`: the server reads its socket from a socket-service thread woken by `zsock_poll()`, which the fuzzer's own context never reaches. `CONFIG_NET_TC_RX_COUNT=0` keeps the parse in the caller's context, so a crash replays.

Proof it can fail: disabling the length check in `dhcpv4_find_client_id_option()` makes `-runs=0` on the `client_id_oversize` seed stop with `stack-buffer-overflow, WRITE of size 32` into the 20 byte `DHCPV4_CLIENT_ID_MAX_SIZE` buffer. Restoring it replays clean. 27044480 executions over 901 seconds produced no report.

Coverage of the path it drives: 75.7% of lines and 35 of 36 functions in `dhcpv4_process_data()` and its callees, over two million runs from the committed corpus. What is left is almost all state one message cannot reach - the ACK arms need a lease already RESERVED or ALLOCATED, and the address validator and provider callbacks are never registered.

The server restarts per case, so a defect needing two messages in sequence is out of reach. Client side: #117144, independent of this one.

## What this changes

A libFuzzer harness for the DHCPv4 server receive path, the counterpart to the client harness in #117144, driving the real server through net_recv_data() from a Zephyr thread.
