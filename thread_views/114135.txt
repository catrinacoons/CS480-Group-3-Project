TITLE: posix: mutex: remove global lock from the acquisition fast path

*--- opening post by kartben (2026-07-20 22:26:13+00:00)
`acquire_mutex()` took a module-global semaphore on every lock, but that lock
is only needed to serialize the one-time auto-init of a statically-initialized
mutex. Pushed it into `to_posix_mutex()` (double-checked re-test) so an
already-initialized handle acquires lock-free, reading owner/type/lock_count
locklessly — exactly as `pthread_mutex_unlock()` already does.

Removes an SMP scalability bottleneck and a single-core priority-inversion window.

**Benchmark** (`qemu_cortex_a53`): 1M uncontended lock/unlock pairs drop from **817 to 508
cycles/pair (~38% fewer)**.

**Tests:** adds a `PTHREAD_MUTEX_INITIALIZER` regression test; `threads_base` passes.

*--- cfriedt (2026-08-04 09:45:55+00:00)
pthread barriers are used for something slightly different, where explicitly known threads need to align on a checkpoint before proceeding. They are kind of handy for some things.

Lazy init of mutex and condition variable resources is a bit of a side-effect to working around a number of things; differently sized mutexes across implementations, the fact that they can be (theoretically) either kernel or user objects (not strictly one or the other), and that mutexes are not futexes (which are limited to userspace and also nicely work on the stack too). Otherwise, we could use static initialization.

Because lazy init does not support static initialization (it's intentionally the opposite) it can create a bit of a race condition when an unknown number of threads try to use the same uninitialized object.
