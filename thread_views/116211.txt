*--- opening post by etienne-lms (2026-08-13 13:40:35+00:00)
Implement `.get_entropy_isr` handler in **entropy_psa_crypto** driver using a random bytes pool filled from a workqueue whose bytes can be consumed from a interrupt handler.

Configuration set the pool size, the threshold to trigger its refilling and the size of the buffer chunk use to refill it.

This added support is useful for example when the entropy PSA Crypto service is implemented in TF-M which has re-entrance constraints preventing reliable calls from a Zephyr interrupt context, notably for example, considering a wireless stack execution constraints.

Add a test for `entropy_get_entropy_isr()` in **tests/drivers/entropy/api/**.

*--- Copilot (2026-08-18 15:30:24+00:00)

*--- Copilot (2026-08-18 15:30:25+00:00)

*--- etienne-lms (2026-08-21 07:08:55+00:00)
It's a bit unclear. I've asked GPT-5.4-Mini *"When to use underrun and when to use underflow when a service is asked a given amount of data but not enough can be provided?"*. Answer:
> Use **underflow** when you mean **a shortage of data available to be read** from a buffer, stream, or queue.
>
> Use **underrun** when you mean **a producer failed to keep up** with a consumer, so the consumer ran out of data to process or output.
>
> **Practical rule**
> * **Underflow = “not enough data came from the source / available to read”**
> * **Underrun = “the supply to a running process fell behind demand”**
> 
> **In your case**
>
> If a **service is asked for a given amount of data but cannot provide enough**, the better term is usually:
>
> * **underflow** if you are describing the **resulting lack of data**
> * **underrun** if you are describing the **service failing to deliver fast enough to keep up with consumption**
>
> **Examples**
>
> * **Buffer underflow**: a decoder requested 1024 bytes, but only 200 were available.
> * **Audio underrun**: the audio device needed data continuously, but the source could not supply it in time, causing a gap.
>
> **Recommendation**
>
> For a **service response that cannot satisfy the requested amount**, use:
>
> * **underflow** if you want to emphasize insufficient available data
> * **underrun** if you want to emphasize failure to sustain output/feed rate

From Wikipedia, *underrun* is sowhat related to bandwidth.
