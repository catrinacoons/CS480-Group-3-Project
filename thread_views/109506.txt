TITLE: net: dns: Fall back to alternate servers

*--- opening post by jukkar (2026-05-20 14:04:24+00:00)
Track per-query DNS server state so unicast lookups can advance to the next configured server when one times out or returns a failure. Keep query-all behavior unchanged by still accepting the first successful response when `CONFIG_DNS_RESOLVER_QUERY_ALL_AVAILABLE_SERVERS` is enabled. Scale the per-query server tracking with `DNS_RESOLVER_MAX_POLL` and make the default additional buffer count follow `DNS_RESOLVER_MAX_SERVERS` so that the resolver has enough buffers for concurrent server connections.

Fixes #109446

*--- Copilot (2026-05-20 14:10:52+00:00)
`dns_handle_server_failure()` can finalize/release the query itself when no more servers remain (it calls `dns_finalize_query()` internally). In that terminal path, execution still falls through to `dns_finalize_query(ctx, i, ret);` below, causing a second release attempt (and potentially a second status path). Consider making ownership explicit: either have `dns_handle_server_failure()` never finalize (caller finalizes based on return), or have it always fully handle terminal failures and make `dispatcher_cb` skip the extra `dns_finalize_query()` when the helper returns a terminal status.

*--- Copilot (2026-05-21 05:44:13+00:00)
dns_query_next_server() repacks the qname from ctx->queries[query_idx].query during fallback. This field is a caller-owned pointer and can be cleared to NULL while a slot is being released (see release_query() behavior), so dereferencing it here can lead to use-after-free or NULL dereference when late responses/timeouts trigger fallback. Consider storing a per-query copy of the query name (or packed qname) inside the pending query slot and/or explicitly bailing out when query == NULL (treat as stale/released) before calling dns_msg_pack_qname().

*--- Copilot (2026-05-21 05:44:14+00:00)
dns_handle_server_failure() can attempt dns_query_next_server() once all pending servers are cleared. If a query slot is already in the "release in progress" state (query pointer cleared, cb possibly still set) due to k_work_cancel_delayable() returning busy, this path can still run and will end up dereferencing ctx->queries[query_idx].query in fallback logic. Add a guard to ignore failures/timeouts for slots with pending_query->query == NULL (stale/released), and avoid triggering further fallback work for already-finalized queries.

*--- Copilot (2026-05-21 06:42:51+00:00)
In `dispatcher_cb()`, failure handling can trigger fallback (`dns_handle_server_failure()` -> `dns_query_next_server()`), which allocates a second buffer from `dns_qname_pool` while `dns_cname` is still allocated from the same pool. With `CONFIG_DNS_RESOLVER_ADDITIONAL_BUF_CTR=0` (pool size = 1), that allocation will always fail, preventing fallback on server failures like `NODATA`/`FAIL`/`REFUSED` and potentially converting the result into `DNS_EAI_SYSTEM`. Consider unref'ing `dns_cname` before calling into fallback logic, or reusing `dns_cname` as the qname buffer for the fallback send.

*--- Copilot (2026-05-21 06:42:52+00:00)
`dns_finalize_query()` always reports the provided status verbatim. This changes the timeout/end-of-results behavior compared to `dns_resolve_cancel_slot()`: when a query has already produced `DNS_EAI_INPROGRESS` callbacks (`cb_called == true`, e.g. DNS-SD/PTR), the previous timeout path would emit `DNS_EAI_ALLDONE`, but the new timeout path (via `dns_handle_server_failure()` -> `dns_finalize_query()`) will emit `DNS_EAI_CANCELED`. Consider mirroring `dns_resolve_cancel_slot()` here (or in the timeout path) so timeouts after partial results terminate with `DNS_EAI_ALLDONE` instead of `DNS_EAI_CANCELED`.

*--- jukkar (2026-05-22 06:51:36+00:00)
The sent variable answers “have we already attempted this server for this query?” while pending answers “is there still an in-flight request to this server right now?”

So for one server, the state typically moves like this:

1. Initial: sent=0, pending=0, failed=0
2. Query transmitted: sent=1, pending=1
3. Reply or timeout/failure handled: sent=1, pending=0, and maybe failed=1

That difference is important because after a server stops being active, we still need to remember that it was already tried. If we only had pending, then once a timeout or negative reply cleared it, that server would look “unused” and fallback could send to it again.
