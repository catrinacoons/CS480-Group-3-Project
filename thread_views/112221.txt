## Summary

Add a Zephyr system timer driver for the NXP RTC (`rtc_jdp`) IP on the MCXE31x family, letting the RTC serve as the kernel tick source. Because the RTC keeps counting across all low-power states, it works as a low-power system timer with no companion timer. The RTC counter driver already exists; this PR adds the system-timer role on the same IP plus the arbitration so the two roles coexist.

## Design

It is a chosen-selected singleton (enabled via `zephyr,system-timer` -> an `nxp,rtc-jdp` node, like `mcux_lptmr_timer.c`), tickless against the RTC's single absolute compare register (RTCVAL), with the free-running 32-bit counter as the cycle counter. A RTCVAL write synchronizes into the slow RTC clock domain and sets `INV_RTC` while in progress (further writes are ignored), so the driver waits for `INV_RTC` to clear before each write per the reference manual. The scheduling horizon is capped at half the counter range so an absolute compare can never wrap past the counter and look like the past (mirroring `mcux_os_timer.c`/`mcux_gpt_timer.c`). The MCXE31x defconfig disables SysTick and derives the clock rate from the chosen node when this timer is selected (prescaler = 1 -> 32 kHz, 1000 ticks/s). The counter driver yields the RTC instance when it is the chosen system timer so both drivers never bind the same hardware. The role is opt-in; the board default (SysTick + RTC-counter calendar) is unchanged.

## Testing

Validated on `frdm_mcxe31b`: `tests/kernel/timer/timer_api` passes 15/15, and `tests/kernel/timer/timer_behavior` passes with zero drift and zero jitter over 10,000 samples (mean exactly 32 cycles/tick, `late_callbacks = 0`). Default-build regressions confirm SysTick stays the default and the RTC counter still instantiates when the RTC is not the system timer.
