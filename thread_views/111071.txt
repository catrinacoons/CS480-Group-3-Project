*--- opening post by krish2718 (2026-06-11 16:28:22+00:00)
net: l2: ethernet: validate MAC after driver start
    
  Commit 481035cf8e1 ("net: ethernet: check mac address when bringing a
  eth iface up") validated the link address before eth->start() was
  called. That broke Wi-Fi interfaces whose MAC is learnt from firmware
  during bring-up (e.g. nRF70 reads it from OTP once the companion
  firmware boots), leaving them unable to admin-up and preventing WPA
  supplicant from registering them. The offending commit was reverted in
  d8065e9f87c to unblock nRF Wi-Fi.
  
  Reintroduce the validation, but run eth->start() first so that drivers
  which populate their address during bring-up have a valid link address
  by the time it is checked. This keeps the useful diagnostic for
  misconfigured MACs while supporting drivers that only know their
  address after start.
  
  A failure of the post-start validation is terminal: net_if_up() fails
  and the interface is left unusable, the same as if eth->start() itself
  had failed. Return -EINVAL directly rather than rolling back with
  eth->stop(), so the behaviour is consistent for drivers that do not
  implement a stop op.

*--- krish2718 (2026-06-15 13:05:35+00:00)
> @krish2718 just add a workaround to your nrf driver by setting a dummy mac in the iface init like @jukkar suggested.

No. Respectfully using a "dummy MAC" address during iface_init as a workaround introduces several silent failure modes and defeats the entire purpose of the original validation feature (commit 481035c):

1. Defeats the Validation Logic: If the driver populates a dummy MAC during init just to satisfy an early check, the Ethernet L2 layer will validate a placeholder. If the firmware subsequently fails to load or fail to retrieve the actual OTP MAC during eth->start(), the interface will stay up using an invalid or duplicated dummy MAC. This brings us right back to the original issue where invalid MACs pass without notice.
2. Race Conditions with Network Management: If the interface initialized with a dummy MAC is exposed to user-space or network management daemons (like WPA Supplicant) before eth->start() finishes swapping it with the real burned-in address, it can cause race conditions where upper layers cache or bind to the wrong hardware address.
3. Power Management Violations: To avoid a dummy MAC, the driver would have to power up the chip, clock the SPI/QSPI buses, boot the companion firmware, and read the OTP during iface_init. Forcing this during early system boot—when the interface might not even be administratively brought up until much later—violates basic low-power embedded design principles.

Delaying validation until the device is actually entering the start phase ensures we are validating the real hardware state without introducing side-channel workarounds.

> > 2. Race Conditions with Network Management: If the interface initialized with a dummy MAC is exposed to user-space or network management daemons (like WPA Supplicant) before eth->start() finishes swapping it with the real burned-in address, it can cause race conditions where upper layers cache or bind to the wrong hardware address.

> as long as the iface is not up, the mac address can be changed at any time with `net_mgmt(NET_REQUEST_ETHERNET_SET_MAC_ADDRESS`, applications or subsystems can't expect that a mac address doesn't change when it is not up.

To look at this from the perspective of upper-layer applications: many subsystems do not explicitly set a MAC address. Instead, they rely entirely on the L2/driver to fetch the authentic OTP address from the hardware. They expect that the moment net_if_up() completes, the interface's MAC is its finalized, true identity.

If a driver uses a dummy MAC placeholder during iface_init to satisfy an early L2 check, and then updates it to the real OTP address inside eth->start(), we create a critical timing hazard for things like DHCP, IPv6 DAD, or WPA Supplicant. If any upper-layer network event triggers or binds to the interface identity right as the state transitions to UP, it risks capturing or caching the transient dummy MAC instead of the real burned-in address.

Overall, using a dummy MAC to bypass a check during iface_init only to overwrite it during eth->start() is entirely pointless for those drivers/devices that actually start the operations in start.

*--- krish2718 (2026-07-07 19:28:56+00:00)
> We could also have a Kconfig that drivers, that have a late setting of the mac, can select and only then check the mac after start and check the mac address otherwise before start. Or then leave it to the driver inside start to check it.

Checking after start() is a strict superset of checking before it: a MAC set in init is still valid after start() (start does not clobber it), so the after-start check catches every statically-misconfigured MAC the before-start check would, and additionally handles drivers that only learn their address during bring-up (nRF70 reads it from OTP once firmware boots). The before-start check catches a subset and cannot validate late-MAC drivers at all.

On avoiding a power-on with a bad MAC: the drivers where powering on is actually expensive (companion chips that clock a bus and boot firmware) are precisely the late-MAC drivers, which have no address to check before start() — so an early check cannot help them. The drivers where you can check early (MAC set in init) are on-die MACs where bring-up is cheap. The early check only ever fires where it does not matter, and is impossible where it would. On top of that, a statically-invalid MAC is a deterministic DTS/build error: you hit it once on the first bring-up during development and get a clear log; in production the address is valid and the path is never taken. There is no recurring runtime cost being traded away.

Given that, a Kconfig only adds a second code path and doubles the behavior we have to reason about and test, for a knob almost no driver would set. So I'd keep it as a single unconditional check right after start() returns.
