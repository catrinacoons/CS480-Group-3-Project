*--- opening post by vignesh-aerlync (2026-06-26 09:39:59+00:00)
The Environmental Sensing sample only published simulated values. Add an optional ESP_USE_HARDWARE_SENSOR Kconfig that, when set, reads a real temperature from a Devicetree alias instead.

ess_simulate() is renamed to ess_update_data(). It resolves ambient-temp0 first, then die-temp0, fetches a sample and converts `SENSOR_CHAN_AMBIENT_TEMP` (falling back to `SENSOR_CHAN_DIE_TEMP`) into the 0.01 degree C units of the ESS Temperature characteristic. Any fetch or read failure falls back to the original simulated data, so the default build is unchanged.

Fixes: #112091

*--- Copilot (2026-06-29 16:00:28+00:00)
The device readiness result is only printed at startup and never used to gate hardware reads. When `temp_dev` is not ready (e.g. the underlying bus/driver failed to initialize), `ess_update_data()` still calls `sensor_sample_fetch(temp_dev)` every second, which is the case the startup message warns about. The closely related `peripheral_ht` sample avoids this by treating an unready device as "no device" and falling back to simulation. Guarding the fetch with `device_is_ready()` makes the fallback to simulated data actually take effect when the sensor isn't ready.

*--- Copilot (2026-06-29 16:00:28+00:00)
Optional: the inline conversion from `struct sensor_value` to 0.01-degree units is duplicated here (and for humidity below) and uses 32-bit arithmetic. The sensor API already provides `sensor_value_to_centi()` (include/zephyr/drivers/sensor.h), which performs exactly this conversion using `int64_t`. Reusing it removes the duplication and avoids potential overflow in the intermediate multiplication.

*--- Copilot (2026-06-29 16:00:28+00:00)
Convention: other sample Kconfig files place `source "Kconfig.zephyr"` at the end, after the application-specific config symbols (see samples/bluetooth/peripheral_ht/Kconfig:16 and samples/bluetooth/peripheral_hids/Kconfig:13). Here it is sourced before the `ESP_USE_HARDWARE_SENSOR` definition. Consider moving `source "Kconfig.zephyr"` below the config block to match the established layout.

*--- vignesh-aerlync (2026-06-30 18:39:06+00:00)
Hi, @sreeramIfx   [here](https://github.com/zephyrproject-rtos/zephyr/pull/112093#discussion_r3488309483) You are completely right, checking `device_is_ready()` inside the 1-second update loop is redundant.  But this is also valid point. To resolve both issues cleanly without adding overhead to the loop, I will updated `main()` to simply set `temp_dev = NULL` if it fails the readiness check at boot. The update loop now just checks `if (temp_dev != NULL)`, which safely bypasses the hardware fetch and triggers the fallback without any redundant readiness checks.
