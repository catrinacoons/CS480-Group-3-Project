*--- npitre (2026-08-12 18:36:22+00:00)
The doc block for `k_queue_peek_next()` should say the lookup is by payload pointer, so with the same pointer enqueued twice through `k_queue_alloc_append()` it always resolves the first occurrence. For user mode that is not a corner case: `k_queue_append()` is not a syscall, so the alloc path is the only way a user thread can fill a queue, and `k_queue_peek_next()` is exposed as one.

```c
		if (z_queue_node_peek(cur, false) == data) {
			ret = z_queue_node_peek(sys_sflist_peek_next(cur), false);
			break;
		}
	}
```

*--- npitre (2026-09-01 19:03:39+00:00)
The benefit is in binding the argument at all, not in the `const`. This macro is already a statement expression, so give `data` a name there and use it in all three places:

```c
#define k_fifo_peek_next(fifo, data)                                                               \
	({                                                                                         \
		void *fpt_data = (data);                                                           \
		SYS_PORT_TRACING_OBJ_FUNC_ENTER(k_fifo, peek_next, fifo, fpt_data);                 \
		void *fpt_ret = k_queue_peek_next(&(fifo)->_queue, fpt_data);                       \
		SYS_PORT_TRACING_OBJ_FUNC_EXIT(k_fifo, peek_next, fifo, fpt_data, fpt_ret);         \
		fpt_ret;                                                                           \
	})
```

`const` on the local is fine and documents that the macro will not reassign it, but the single evaluation is what fixes the problem: a caller writing `k_fifo_peek_next(f, next_candidate())` currently calls that function three times, and the traced pointer can differ from the one looked up. The `fpt_` prefix matches the existing `fpt_ret` so it will not collide with a caller's identifier.

`fifo` is still expanded three times, but `k_fifo_peek_tail()` above already does that and the argument is an object, so I would leave that alone rather than grow the diff.

*--- npitre (2026-09-01 19:03:39+00:00)
Yes, and that follows from the restructure rather than being a separate change: once the next-node lookup happens inside the loop body, `cur` cannot be NULL there, so `sys_sflist_peek_next_no_check()` is the honest call and it is documented as the faster one for exactly that case.

Two things worth keeping in mind. Its NULL *return* is still possible when the match is the last element, and that is fine because `z_queue_node_peek()` maps NULL to NULL. And with the lookup inside the loop, `ret` stays NULL on the not-found path without any reliance on `sys_sflist_peek_next(NULL)`, which is the part I was really after.
