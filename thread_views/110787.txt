OK, this was a tough one! Here are some notes compared to the original RFC:
1. I was unable to implement `gpio_fast_send_stream()`. The timing requirements for a driver like WS2812 are too tight to abstract the data out into a struct and for loops. I was only able to make it work by creating a specific 2-operations-per-bit set/clear mode, which defeats the point of the abstraction. It is likely possible, but will take a lot more work and I think should go in a followup PR.
2. The only way I could make the timings reliable across all platforms was to use `nop`.
3. I could not use `LISTIFY()` because it created a mess of Kconfig math. We can now automatically calculate timing offsets via the number of CPU cycles required for set and clear in the header/source, so the WS2812 driver no longer requires per-board timing config in Kconfig/DTS.
4. When implementing future vendor Fast GPIO drivers, it is really a **requirement** that it is tested on real hardware. There are so many edge cases where you may need `__ramfunc` or calculating the cycle offsets are weird. The good thing is, **none of these edge cases are visible from the user-facing API.**
5. The number of cycles to do operations varies per platform, but **the driver can fully realize if timings can be met at compile time.**

The part I am really proud of: I have verified this works on **6 different platforms!**
- Adafruit Circuit Playground Express: `sam0`
- Adafruit Feather ESP32: `esp32`
- Adafruit KB2040: `rpi_pico`
- Teensy 4.0: `mcux`
- STM32 Nucleo-F401RE: `stm32`
- nRF52840 Dongle : `nrf52840`

All of these work without custom timing in DTS.

*--- DaAwesomeP (2026-07-17 17:22:10+00:00)
OK, there's 3 parts here:

#### Frequency

Frequency is determined from the provided `GPIO_FAST_CPU_FREQ` var (which comes from DT). A driver uses `GPIO_FAST_NS_TO_CYCLES()` to convert from nanoseconds to cycles (this macro uses the correct frequency from `GPIO_FAST_CPU_FREQ`) at compile time.

Currently, this only supports one frequency, so backends need to implement `gpio_fast_pre_stream_<compat>()`/`gpio_fast_post_stream_<compat>()` if clock control is enabled to ensure the frequency is correct. We could add a `CONFIG_GPIO_FAST_CPU_FREQ` to Kconfig to allow the user to override the frequency determined at compile time. We could make it possible for a driver compile for multiple frequency options at compile time (and branch at runtime before the timing-critical section), but this would be in a followup PR.

#### SOC-specific Operation Cycle Counts

The cycle counts per operation are specific to the permutation of 1) the SOC, 2) the particular GPIO peripheral, and 3) the specific implementation written in the backend for manipulating that peripheral. Frequency does not affect this count, although we subtract these counts from the result of `GPIO_FAST_NS_TO_CYCLES()` at compile time to determine the `nop` timing.

Since these are SOC-specific/only on-SOC GPIO peripherals, I think it makes most sense to add an `#ifdef` per SOC that adjust these cycle counts by SOC (same way different SOCs are handled in the general GPIO drivers). I don't think it makes sense to put these in DT, as they are specific to the function implementations written in the driver, not generalization to a SOC as a whole. I have already done this one one case: the STM32 backend has relies on `CONFIG_SOC_SERIES_STM32F1X` and adjusts timings/implementation based on that (which is the same way it works in the general STM32 GPIO driver).

I will work on adding these SOC `#ifdef`s.

#### Drive Strength and Other Peripheral-Specific Features

The drive strength does not affect the number of cycles required to set/read a GPIO register, so it does not affect the cycle timings as implemented. Most protocols, like the WS2812, have some tolerances for different slew rates; in my testing I did not need to offset for slew rate differences between GPIO peripherals for WS2812. For other applications that require more precise timing requirements, we can easily add constants like `GPIO_FAST_SET_SLEW_TIME_NS_<compat>_gpio` that drivers can make use of if necessary (can add in followup PRs). The actual computation of the timings is up to the downstream driver; it uses a combination of the provided frequency, nanosecond conversion helpers, and set/clear/toggle timings to do this. Additionally, drivers/users can override timings in DT with optional per-downstream-driver parameters like `delay-t0h` like the WS2812 driver offers (see #111218).

There is nothing restricting us from adding more DT params (like `fast-gpio-drive-strength` or `fast-gpio-stm32-drive-strength`) in followup PRs that would be consumed by `gpio_fast_configure_<compat>_gpio()`. Since these would go in DT, they can be known at compile time and affect timing constants (like `GPIO_FAST_SET_SLEW_TIME_NS_<compat>_gpio` above). Since the timings need to be known at compile time, I don't think you can switch drive strength at runtime if it affects the timings. I also can't see a reason to need to switch drive strength modes more quickly than the standard GPIO API, although that could easily be added as a method to the backend.

*--- DaAwesomeP (2026-07-21 17:45:39+00:00)
> @DaAwesomeP to take a look at how logging subsystem solves the out-of-tree problem

OK, I took a look at this. To recap, the current solution I have implemented:

1. User enables `CONFIG_GPIO_FAST_OUT_OF_TREE_BACKEND`
2. User provides `zephyr_gpio_fast_impl_oot.h`
3. This header contains more includes or the backend-specific headers and `#define` statements.
4. This header is included in the main Fast GPIO header, which allows all downstream drivers (i.e. WS2812) to use it at compile time.

The tracing backend seems to work _exactly_ like this (`CONFIG_TRACING_CUSTOM` + `zephyr_custom_tracing.h`):
https://github.com/zephyrproject-rtos/zephyr/blob/c01ba2033999385e5306b38deddc2fe9501daf74/include/zephyr/tracing/tracing.h#L19-L28

In contrast, the logging backends rely on choosing at runtime:

1. OOT module defines a logging backend struct with function pointers for its API (e.g. `log_backend_msg_process`).
2. OOT module registers it with `LOG_BACKEND_DEFINE()`, which places the struct into a dedicated linker section via `STRUCT_SECTION_ITERABLE`.
3. At runtime, the logging core iterates all backends in that linker section using `STRUCT_SECTION_FOREACH` and dispatches log messages through the function pointers.
4. No in-tree header modification or `#include` of OOT code is needed. The linker collects everything automatically.

This will not work because we need the linker and preprocessor to find all of the methods/macros at compile time (no function pointers).

Another method I can think of (which would work, but more difficult to maintain and I think new to Zephyr):

1. User creates a header with the backend-specific headers and `#define` statements.
2. User includes the header through a CMake helper like `include_fast_gpio_backend(file)`. This helper can be called multiple times.
3. CMake generates a header that includes each files specified by `include_fast_gpio_backend()`.
4. Main Fast GPIO header includes this generated header.

This method would allow a user to include multiple backend headers without needing to assemble them into one header or include them from one header. However, I don't think creating a single `zephyr_gpio_fast_impl_oot.h` is difficult enough to add this complexity (and it matches the tracing subsystem).
