Potential null pointer dereference. The code accesses `chan->qos` without checking if `chan` or `chan->qos` could be NULL. While `store_cis_info` (which runs before this function) also accesses these pointers without checks, it would be safer to add null checks here to prevent crashes if the function is called in unexpected states or if the calling order changes in the future.

Consider adding null checks:
```c
if (chan == NULL || chan->qos == NULL) {
    LOG_WRN("Cannot log CIS info: chan or qos is NULL");
    return;
}
```

	const struct bt_iso_chan *chan = iso_conn->chan;
	if (chan == NULL || chan->qos == NULL) {
		LOG_WRN("Cannot log CIS info: chan or qos is NULL");
		return;
	}
	const struct bt_iso_info *info = &iso_conn->info;

*--- Copilot (2026-02-11 14:29:38+00:00)
The newly added CIS established logs print `central->latency` / `peripheral->latency`, but those fields are currently populated from `evt->c_latency` / `evt->p_latency` using `sys_get_le16()` even though the HCI event fields are 24-bit (`uint8_t [3]` in `bt_hci_evt_le_cis_established`). This will truncate the latency and makes the new debug output misleading. Consider switching the latency extraction in `store_cis_info()` (and thus v2 as well) to `sys_get_le24()` so the logged and stored transport latencies match the controller values.
